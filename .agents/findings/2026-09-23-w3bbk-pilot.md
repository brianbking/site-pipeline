# W3BBK.us pilot — platform findings (2026-09-23)

Answers to the plan's Task 10 questions, from PR brianbking/W3BBK#1 and the staging bootstrap.

1. **What 403s Node's `fetch` on the zones?** Not yet identified. Node `fetch` gets
   `cf-mitigated: challenge` on every family zone whatever its user agent; curl with a browser UA
   gets 200, so it keys on the client fingerprint (Bot Fight Mode is the likely cause). Open item:
   read Security → Events for one challenged request. The pipeline no longer depends on the answer,
   because every Node check runs against `workers.dev`.

2. **Do `_headers` rules apply to Worker responses from `env.ASSETS.fetch`?** Yes. On the real
   `w3bbk-staging` deploy, `/` and `/.well-known/agent-card.json` carry the `_headers` CSP, and the
   Worker's own `X-Robots-Tag` wins over the `_headers` value. `wrangler dev` behaves the same.

3. **Do preview URLs work with `workers_dev: false` + `preview_urls: true`?** Only once the
   Worker-level setting is on. `wrangler versions upload` does not apply `preview_urls` from config:
   the first run printed a Version ID and no preview URL. `w3bbk` needed Settings → Domains &
   Routes → Preview URLs → Enable in the dashboard. `wrangler deploy --env staging` did enable it
   for the new staging Worker. Every wave's setup checklist needs this toggle.

4. **Was a missing `run_worker_first` why `src/worker.js` never negotiated?** Yes, as far as the
   evidence goes. With `run_worker_first: true` the same kind of Worker negotiates on staging and on
   the PR preview. Wave 4 re-confirms on BrianBK.ing and JillK.ing.

5. **Real wrangler output (4.137):**
   - `versions upload` prints `Worker Version ID: <uuid>`, plus `Version Preview URL:` and
     `Version Preview Alias URL:` lines only when preview URLs are enabled.
   - `deployments status` prints `Version(s):  (100%) <uuid>`, which matched the parser.

6. **Are `workers.dev` preview URLs free of the zone challenge?** Yes. Node `fetch`, Playwright and
   Lighthouse all reached `https://pr-1-w3bbk.catastrophic.workers.dev` in the `live` job.

## Other findings

- **Preview URLs are forced `x-robots-tag: noindex` by the platform**, overriding the Worker's
  header. Lighthouse `is-crawlable` therefore fails on every preview, so v0.1.3 skips it.
- **Preview hosting distorts Best Practices.** Hugo emits absolute `https://w3bbk.us/...` asset URLs,
  and on the preview origin the site's CSP (`script-src 'self'`) blocks them, producing a console
  error. v0.1.3 judges BP and SEO against production (0 tolerance) instead of an absolute 95.
- **Lighthouse flags `robots.txt` as invalid** because of the `Content-Signal` / `Content-Usage`
  lines. This happens in production too, and it's accepted: the lines are intentional.
- **Visual regression uses pixelmatch `threshold: 0.1`,** which absorbed the footer opacity change
  0.6 → 0.7 as 0.000%. That's fine for layout regressions, but it's blind to subtle colour shifts.
- **npm writes `git+ssh` into `package-lock.json` for a GitHub git dependency**, even when
  `package.json` says `git+https`. `npm ci` still succeeds with SSH disabled, because pacote fetches
  GitHub dependencies as https tarballs. `npm install <url>` also rewrites `package.json` to the
  `github:` shorthand, so re-edit it afterwards.
- **Two `wrangler dev` processes in one project deadlock on `.wrangler/state` SQLite** (`SQLITE_BUSY`).
  Give the second one `--persist-to .wrangler/state-staging`.
- **W3BBK's baseline, now fixed:** Accessibility 87 → 100 after `.mastfoot` opacity 0.6 → 0.7.
